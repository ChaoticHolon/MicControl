# MicControl roadmap and platform plans (developer's plans; nothing built yet)

MicControl grows from mic muting into voice processing and mixing. None of it is in 1.0; keep the current design open to it.

`ROADMAP.md` at the repo root is the readable, structured version of these plans for people. When a plan changes, update both, so they never disagree.

## Packaging and platforms
- Arch/CachyOS: two AUR `PKGBUILD`s. `miccontrol` builds from the source tag with `dotnet publish`; `miccontrol-bin` repackages the release's `miccontrol-<version>-linux-x64.tar.gz`. Framework-dependent on Arch's `dotnet-runtime`, installed system-wide (`/usr/lib/miccontrol`, `/usr/bin/miccontrol` launcher, `/usr/share/applications` desktop file, hicolor icons); settings in `~/.config/MicControl`. Updates come from pacman/shelly/paru/yay. Create and maintain pacman repo later.
- Debian/Ubuntu: a `.deb` later, built in CI with `nfpm` (one config can also emit an Arch package).
- Release tag outputs: Windows setup.exe, Linux tarball, signed `SHA512SUMS`; then bump the AUR `pkgver` and checksums.
- Timeline: Linux (CachyOS) after the Windows audio engine, enhancement and per-app capture (it may slip past this year), macOS next year.
- macOS plan: Avalonia head project, CoreAudio mute, CGEventTap hotkeys (needs Input Monitoring/Accessibility permission), floating click-through overlay window.
- **Dev's decision: no money to Apple for a developer account, so no notarization. Will likely be distributed as:
  - A Homebrew tap (GitHub repo) whose formula builds from source with `dotnet publish`: locally built apps aren't quarantined, so Gatekeeper doesn't block them, and `brew upgrade` handles updates. Not the official homebrew-cask, which is phasing out casks that fail Gatekeeper.
  - A `.dmg` on GitHub Releases for non-Homebrew users, documenting the one-time System Settings → Privacy & Security → "Open Anyway" step.
  - Sign with a self-made certificate kept in CI secrets (not Apple-issued): a stable identity keeps the Input Monitoring/Accessibility grants across updates. Ad-hoc signing (`codesign -s -`) would satisfy Apple Silicon but loses the grants on every update.
  - In-app updates for the `.dmg` via NetSparkleUpdater behind `IUpdateService` (files the app downloads itself aren't quarantined); Homebrew installs report "managed by Homebrew".

## Features
- **Order** (developer's decision): 1.0.1 (tests the signed updater) → device aliases and the other 1.x features below → audio engine → speech enhancement → per-app capture → Linux (which carries the engine over to PipeWire) → output buses. Everything up to per-app capture is Windows work done BEFORE Linux; only the buses come after it.
- **Mute never depends on the engine** (developer's rule): if the engine fails or a route breaks, the app falls back to the Core Audio endpoint mute, and push-to-talk fails muted.
- **1.x features, before the engine**: device aliases; settings export/import; a mic diagnostics page (privacy setting blocking the mic, exclusive mode held by another app, clipping, hardware mute switch, sample rate; later engine latency, CPU and dropouts); hotkey conflict warning; an opt-in beta update channel (signed pre-releases); per-app profiles (mode, hotkey, mic follow the foreground app; game mode for full-screen games); a fallback mic matrix (next mic takes over when one is unplugged, switches back when it returns) and an output switcher; default/communications device sync; XInput controller buttons as hotkeys; command-line control (`--toggle`, `--mute`…); push-to-talk release tail, double-tap to latch and timed mute; an opt-in overlay level ring that also warns when you talk while muted; "mic in use" awareness (which apps are listening; overlay only while in use); translations and an accessibility pass; an "on air" light over local MQTT/Home Assistant (off by default, LAN only; README's Privacy section must mention it).
- **Local control API**: one local-only interface (named pipe/localhost, with OSC) that MIDI, the CLI and every plugin use. Plugins, each in its own repository: OBS, Discord (Vencord/BetterDiscord; control only: mute sync, input selection), Stream Deck, Bitfocus Companion, Touch Portal, Loupedeck, Mumble, TeamSpeak, a KDE Plasma widget. Never Teams or any other Microsoft proprietary software (developer's principle).
- **Audio engine**: a separate `MicControl.Audio` project behind `MicControl.Platform` interfaces, with WASAPI and ASIO devices from the start (ASIO wanted soon; Steinberg's ASIO SDK is GPLv3-licensable since Oct 2025, and `NAudio.Asio` is MIT; many ASIO drivers take one client, and ASIO bypasses the Windows mixer, so its mute happens in the engine). A voice chain (gate, compressor, limiter, EQ, auto level) with shareable presets ("Broadcast", "Podcast", "Clean") and VST3 effect hosting (VST3 SDK is MIT since 3.8); sidetone; ducking; a "how do I sound" record-and-playback test. 10 ms blocks (480 samples at 48 kHz) through preallocated ring buffers; the audio thread never allocates and runs at MMCSS "Pro Audio" priority. Keep NAudio (MIT) for devices; for a cross-platform engine consider miniaudio (public domain/MIT-0, P/Invoke). Not CSCore (abandoned, MS-PL) or BASS (proprietary).
- **Speech enhancement**: GPU-first via ONNX Runtime (DirectML on Windows, CUDA/TensorRT, Core ML on macOS), with posted system requirements and a benchmark on the user's own machine before it can be turned on (it stays off, with the reason, if it can't keep up). The developer rejects DeepFilterNet (unmaintained) and RNNoise (robotic). First prototype ClearerVoice-Studio's models (MossFormer2) streaming in a sliding window, measuring latency (target 20-40 ms look-ahead) and quality; ClearerVoice also suits cleaning saved clips. Echo cancellation: WebRTC AEC3. Windows 11's Voice Clarity is a possible light fallback. Check every model's licence (e.g. Meta's denoiser weights are CC-BY-NC: not shippable).
- **Per-app capture** (Discord, Spotify… by PID): WASAPI process loopback (`ActivateAudioInterfaceAsync` with `AUDIOCLIENT_ACTIVATION_TYPE_PROCESS_LOOPBACK`, Windows 10 2004+, our minimum), likely our own interop feeding NAudio; macOS ScreenCaptureKit (13+) or Core Audio process taps (14.4+); PipeWire natively.
- **Routing to other apps** (developer's decision): MicControl never bundles a virtual audio driver. Every Windows virtual audio device is a kernel driver (our own would need an EV certificate and Microsoft attestation signing, a yearly cost), and the SysVAD-derived ones (e.g. VirtualDrivers/Virtual-Audio-Driver) carry Microsoft's MS-PL sample code. Users who want the feature install a virtual cable themselves (VB-Audio Virtual Cable, Virtual-Audio-Driver…); the processed mic and the buses route into it, and the feature turns on only when one is detected (otherwise it says why it's off). Detection is generic, not a fixed list. OBS gets its own GPL plugin that only carries audio into OBS; control goes through OBS's local obs-websocket. On Linux, PipeWire lets the app create its own virtual devices, so no cable is needed there. A setup wizard detects the cable and OBS, sets up the route and runs the sound test.
- **Routing levels** (one setting): Off (default: mute only, no engine) → Simple (one output: processed mic to the virtual cable) → Streamer (three buses: Monitor, Stream, Record) → Advanced (any number of inputs and buses, configured in a normally hidden panel). The engine and settings model N buses from the start. Inputs: hardware (WASAPI/ASIO), a virtual cable set as Windows' default output (system audio), single apps, app groups, later network (VBAN-compatible). Matrix UI with colour-coded routes; per-bus mute ("stream mute"); a panic button mutes every bus.
- **Streamer support**: detect OBS/Streamlabs (process, then obs-websocket for live/recording) and offer the Streamer level once, never switching silently. OBS actions (switch scene, start/stop stream or recording, save replay, toggle source, markers) are targets in the existing action system (custom hotkeys, profiles, MIDI, control API, panic button); no automation engine of our own (Streamer.bot and others do that). Scene-aware mute (e.g. "BRB" mutes the Stream bus), stream-safe music (chosen apps on Monitor but off Stream while live), one-click OBS setup. Clip recording only through OBS/Streamlabs (replay buffer), never a recorder of our own.
- **Device aliases**: custom names for devices, keyed by device id in settings (small; could ship in a 1.x).
- Backlog: mute on lock/sleep (Toggle mode); portable mode; OpenRGB lighting (GPL-2, low priority); local live captions (Whisper via ONNX Runtime, offline, also an OBS caption source); a soundboard (clips into the Stream bus or the cable); macOS audio core (Core Audio HAL, ScreenCaptureKit); network audio (VBAN-compatible).
