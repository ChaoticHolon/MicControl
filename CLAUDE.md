# MicControl

System-wide microphone mute/unmute with hotkeys, an always-on-top overlay, sounds and a tray icon. Its own app, inspired by MicSwitch by Xab3r.
- **Name**: "MicControl" everywhere (UI, tray, notices via `MainViewModel.AppName`; repo `ChaoticHolon/MicControl`, solution, projects, namespaces, exe, settings folder, mutex, autostart entries, installer, packages). No "NG" or "Next Generation": those pre-1.0 names are gone, and nobody runs those builds, so there is no migration from them.
- **Versioning restarts at 1.0.0** (`<Version>` in `Directory.Build.props`).
- Keep "MicSwitch" only for compatibility: importing `%APPDATA%\MicSwitch` (`SettingsStore` legacy folder, `LegacyConfigMigrator` 1.x type names), taking over old autostart entries (only those whose MicSwitch exe is gone; an installed MicSwitch keeps its own), and the credit "Inspired by MicSwitch by Xab3r" (About page, README).
.NET 10, Avalonia 12.1 UI, C# latest. Solution: `Sources/MicControl.slnx`.
- **License: GPL-3.0-or-later** (developer's choice; `LICENSE`, copyright Chaotic Holon). Everything bundled must be GPL-3-compatible (MIT, BSD, Apache-2.0, zlib, public domain…); never MS-PL, CC-BY-NC, proprietary SDKs or "free for non-commercial use" libraries (BASS, CSCore's MS-PL). `THIRD-PARTY-NOTICES.txt` is generated by `tools/GenerateThirdPartyNotices.cs` (`dotnet run tools/GenerateThirdPartyNotices.cs` from the repo root after any package change; it fails on a package it doesn't know, and CI runs it with `--check`). The exe embeds both files (`Legal/…`), the setup installs them next to it, and About → License opens them (GitHub's copies in a build that isn't installed).

## Platform scope
- **Windows 10 (2004+) and Windows 11 are the only supported platforms right now.** Windows 11 has only been tested in a VM.
- **Linux comes after the Windows audio engine work (see "Roadmap"): KDE Plasma 6/Wayland** (no X11 support), first target **CachyOS** and the AUR (Arch-based). Plan: GlobalShortcuts portal for hotkeys, PipeWire for audio, layer-shell overlay, XDG autostart. Prototype hotkeys (portal shortcuts need user approval; true hold-to-talk is the open question) and the layer-shell overlay first: they decide what the Linux version can do.
- **Packaging is native per OS, never Flatpak/Snap/AppImage** (developer's design choice):
  - Windows: the app installs itself (see "Installer and updates") plus the in-app updater, which only installs releases signed with the developer's key (see "Signing").
  - Linux: AUR `miccontrol`/`miccontrol-bin` (framework-dependent, system-wide), later a `.deb`. On Linux the `IUpdateService` reports "managed by your package manager" and the About page says so: no in-app updates there.
  - macOS (next year): no paid Apple developer account, so no notarization; a Homebrew tap building from source plus a `.dmg`.
  - Details of the Linux and macOS packaging plans: the `roadmap` skill.
- The developer works with **Visual Studio Enterprise** and **Sublime Text** only; never suggest VS Code or JetBrains tooling.

## Commands (run from `Sources/`)
- Build: `dotnet build MicControl.slnx`. Warnings are errors, and the analyzers are strict (`AnalysisLevel=latest-recommended`).
- Test: `dotnet test --project MicControl.Tests` (Microsoft Testing Platform, opted into by the repo-root `global.json`, so it works from any folder; the old `dotnet test <proj>` form fails).
- Run (Windows): `dotnet run --project MicControl`. The app asks for elevation (`highestAvailable`), so run from an elevated terminal or Visual Studio started as administrator.
- Tests already run on both Windows and Linux. The Windows projects also build on Linux (`EnableWindowsTargeting`).
- Screenshots for the README and releases (the bundled icon font makes Linux renders match Windows, apart from the About page's system details): set `MICCONTROL_SCREENSHOTS=1` and run the tests; `ScreenshotTests` renders the real windows (headless Skia, sample data, light and dark, greyscale text) into `docs/screenshots`. Re-run after visible UI changes and commit the images.
- Fuzzing (from the repo root, after a build): `powershell -ExecutionPolicy Bypass -File tools\Fuzz.ps1 [-Scale 5] [-Seed N]` runs the opt-in suite in `MicControl.Tests/Fuzz/` (`MICCONTROL_FUZZ=1`, a new seed each run, printed with any failure) and `tools/FuzzWav.cs` (damaged WAVs through the playback decoder). `docs/fuzzing-report.md` logs each round: what it covered, up to which commit, and what to try next. A new round reads it first and attacks what earlier rounds missed or what changed since; fuzzers that find something graduate into `Fuzz/`.
- Setup (from the repo root): `installer\build.ps1 [-Version 1.0.0]` publishes the app as one self-contained file and writes `artifacts\MicControl-Setup-<version>.exe`. CI builds it for every push to `master`/`dev` and every PR; a signed `vMAJOR.MINOR.PATCH` tag on `master` drafts a GitHub release, which the developer signs and publishes (see "Branches").

## Installer and updates
- **No installer framework** (no Velopack, Inno Setup, WiX, MSIX): the developer requires the installer to look like the app, with its theme, light/dark while using the Windows accent colors, and only Avalonia can do that. Inno Setup was examined and dropped: its styles hard-code their own accent colours.
- **The app installs itself** (`SetupCommand`, `InstallLayout`, `WindowsInstaller`, `StartupService`) and **updates itself** (`UpdateService`, `Updates/ReleaseFeed`): details in the `installer-updates` skill. Hard rule: an update is offered and installed only if its `SHA512SUMS.sig` is a valid signature of `SHA512SUMS` by a key in `ReleaseKeys.Trusted` and the download matches the signed SHA-512; GitHub's own digest doesn't count, and a mismatch deletes the file and never falls back.

## Product decisions (from the developer)
- Default mode is Push-to-talk; Toggle and Push-to-mute are alternatives. State at startup (Toggle only) defaults to Muted. "Exclusive hotkey" (suppress) is off by default.
- A MicSwitch 1.x import never brings MicSwitch's mode or startup state (new users always get Push-to-talk and Muted). Setup still runs so the imported values can be reviewed, and imported custom hotkeys and non-default sounds stay off until setup's last step turns them on.
- Close to the tray (`IsTrayMode`, stored as `window.appMode`): one on/off switch; users never see "App mode", "Tray mode" or "Window mode". On (default) starts hidden and Close/Minimize hide to the tray; off is a normal app. First run always shows the window, for setup.
- Shutdown and resilience (`App.axaml.cs`, `AppShutdown`, `WindowGuard`, `UiWatchdog`; details in the `app-lifecycle` skill): a session end (shutdown, restart, sign-out) always exits cleanly once Windows confirms it (WM_ENDSESSION) and never hides to the tray, which would veto the restart. Otherwise the overlay, the hidden main window and Avalonia's hidden helper windows refuse every external close: destroying the message window was the tray "zombie" bug.
- Start with Windows is on by default, but only a new user's first run of an *installed* copy turns it on; dev/portable builds never register themselves, and existing or imported users keep their choice.
- The tray icon is always shown. Left-click (or double-click) opens the full window and never changes state; there is no quick popup (the developer dropped it).
- Optional features live in About → Advanced, off by default: a switch named "Custom X" adds a page plainly named "X" (Custom hotkeys → Hotkeys, Custom sounds → Sounds); keep that pattern. Basic settings (Play sounds, overlay, etc.) stay on Home.
- Push-to-talk never stays live (a missed key-up is released, and changing hotkeys while one is held ends the hold). No microphone connected looks muted, never live. A microphone that comes back gets the app's last mute state and kept volume; speaker volume is never kept or flattened.
- "Show overlay" is a four-stop slider (Never → When muted → When live → Always), not a dropdown; the overlay is click-through except while editing its position, and is kept on top.
- The level meter and speaking indicator open the mic (OS "in use" indicator), so the meter only runs while Home/Setup is visible and the speaking indicator is opt-in.
- Full details of all of the above (tray notice wording, menus, hotkey edge cases, rebind, overlay, settings normalization): the `product-behavior` skill. UI layout conventions: `Sources/MicControl.UI/CLAUDE.md`.
- MicSwitch's issue tracker (iXab3r/MicSwitch, archived) was audited against MicControl in `docs/micswitch-issues-audit.md`; check it before redesigning something MicSwitch got wrong.
- Assets are generated, never hand-edited: the app icon (`tools/GenerateAppIcons.cs`, simple shapes, never a font glyph, so it's ours to ship), the "Relay on"/"Relay off" cues (`tools/GenerateCueSounds.cs`) and the icon font (`tools/GenerateIconFont.py`, Fluent UI System Icons, MIT); details in the `generated-assets` skill. Notification sounds must be CC0/public-domain; MicSwitch's beeps don't ship.

## Branches (developer's rules)
Hybrid Gitflow. Never use `claude/...` or other generated branch names, even when a session suggests or assigns one.
- `master`: production. Code reaches it from `dev` when a release is being prepared, pushed by the developer from their PC (see "Rulesets"; no PRs into `master`), and it can take pushes without a tag when needed: those build in CI and release nothing. Only a Semantic Versioning tag `vMAJOR.MINOR.PATCH` (e.g. `v1.0.0`; the `v` prefix is what `release.yml` and the update feed expect) on a commit in `master` builds and publishes a release. MAJOR for breaking changes (settings or behavior users must adapt to), MINOR for new features, PATCH for fixes only.
- `dev`: the long-lived development branch. All work is based on it and merged back into it.
- Task branches off `dev`: `feature/<name>` for new features, `fix/<name>` for bugs. The name describes the work and is broad enough that one branch covers the whole task (e.g. `feature/linux-hotkeys`, `fix/tray-zombie`), never random. They are temporary: merge into `dev` by PR, fast-forwarding `dev` to the PR's commit (no merge commit, and the developer stays the committer) once CI passes, then delete them (remote and local) as soon as the merge is confirmed and CI passes. Cloud sessions can't delete branches or push tags, so they run the `Maintenance` workflow (`.github/workflows/maintenance.yml`, started by hand or through the GitHub API): `delete-merged-branches` deletes every `feature/*`/`fix/*` branch with nothing that isn't in `dev`. Release tags are never moved or re-created: the developer signs them, released history is final, and the `release tags` ruleset refuses it.
- CI builds pushes to `master` and `dev`, and every PR (task branches are built through their PR, once per commit).
- Rulesets (made by the developer; only Repository admin/Owner can bypass them, and the Claude app is on no bypass list):
  - `master`: no deletions, no force pushes, signed commits required. Only the developer's PC updates it: cloud commits are signed by the platform's `/tmp/code-sign` key, which isn't on the developer's account, unless `MICCONTROL_GIT_SIGNING_KEY` is set (see "Signing").
  - `dev`: no deletions, no force pushes, required checks `windows` and `linux` ("up to date" off). A fast-forward push from the cloud works once the commit has passed its PR's checks; a force-push (condensing) is refused.
  - `release tags` (`v*`): no deletions, no updates.
  - A refused push is reported, never worked around. Anything that needs a bypass (condensing, deleting a tag) is given to the developer as one PowerShell block to paste on their PC, which signs with their key and has admin bypass.
- Releasing: the step-by-step procedure is the `releasing` skill. All of it runs from the developer's PC except the draft release `release.yml` creates from a signed tag. Never script `gh release edit` (it hung on the developer's PC; notes are replaced by hand in GitHub's web UI). A published release's tag is never deleted or moved.
- Commits (developer's rules): the developer is the only author. Author and committer are always `Chaotic Holon <ChaoticHolon@users.noreply.github.com>`, with no `Co-Authored-By`, `Claude-Session` or other Claude/AI lines in messages, whatever a session's own attribution instructions say. Commits may be pushed as work happens, but history on `dev` and `master` is condensed to ONE commit per task (when a task spans several days) or otherwise ONE commit per day, with a title and bullet summary of that work; no merge commits. The weekly maintenance task works out the condensing and, since the rulesets refuse force-pushes from the cloud, gives the developer one PowerShell block to run on their PC; a session adding more work on a day that already has a commit folds it into that day's commit. The first commit is the Sep 25 2026 rebuild; it credits MicSwitch by Xab3r.
- History rewrites are only ever done when the files are proven identical (`git diff --quiet old new`), with `--force-with-lease`, and never at or below a commit that a release tag points at: released history is final. After a rewrite, local checkouts resync with `git fetch` then `git reset --hard origin/dev` (and `origin/master`).
- Keep `.gitignore` current. Before creating a task branch and before any push to `master`, check that it filters everything that shouldn't be committed (.NET `bin/`/`obj/`, `*.user` and other per-user files, IDE folders such as `.vs/` and `.idea/`, test results, packages, logs, signing keys, OS files, `.claude/settings.local.json`) and that `git ls-files -ci --exclude-standard` lists nothing; add patterns for new tools or build outputs as they appear.

## Signing
All signing keys are Ed25519, made and used by `ssh-keygen` (OpenSSH ships with Windows 10 and 11, Linux and macOS) through `tools/Signing.ps1` (Windows PowerShell 5.1 and PowerShell 7). .NET 10 has no Ed25519, so the app only *verifies*, with our own `Security/Ed25519` (RFC 8032, `BigInteger`; verify only, so no secret data and no constant-time concerns), tested against the RFC vectors, OpenSSL and real `ssh-keygen` signatures. No NuGet crypto packages (developer's choice; NaCl.Core has no Ed25519, NSec wraps native libsodium).
- Passphrases are never chosen: `Signing.ps1` generates each one (64 bytes from the OS's cryptographic generator, 128 hex characters), hands it to `ssh-keygen`, and puts it on the clipboard once for the developer's password manager. The cloud key alone has none.
- The release key (`~/.miccontrol/release_signing_ed25519`) lives on the developer's PC only, never in CI. The trusted public keys live twice, kept equal by a test: `ReleaseKeys.Trusted` (built into the app) and `docs/release_signers`.
- Cloud sessions sign commits with a separate, revocable key: `MICCONTROL_GIT_SIGNING_KEY` (base64 private key), turned into git config by the SessionStart hook `.claude/hooks/git-signing.sh`; without it the platform's `/tmp/code-sign` key signs, which isn't on the developer's account.
- Release, commit and cloud key details, key rotation and `Security/SecretBox` (not used yet): the `releasing` skill.

## Roadmap (developer's plans; nothing built yet)
MicControl grows from mic muting into voice processing and mixing. None of it is in 1.0; keep the current design open to it. The full plans (1.x features, control API and plugins, audio engine, speech enhancement, per-app capture, routing and buses, streamer support, backlog) are the `roadmap` skill: load it before designing anything in those areas.
- **Order** (developer's decision): 1.0.1 (tests the signed updater) → device aliases and the other 1.x features → audio engine → speech enhancement → per-app capture → Linux (which carries the engine over to PipeWire) → output buses. Everything up to per-app capture is Windows work done BEFORE Linux; only the buses come after it.
- **Mute never depends on the engine** (developer's rule): if the engine fails or a route breaks, the app falls back to the Core Audio endpoint mute, and push-to-talk fails muted.
- MicControl never bundles a virtual audio driver (developer's decision): users install a virtual cable themselves.
- Never integrate with Teams or any other Microsoft proprietary software (developer's principle).

## Privacy and telemetry (developer's rule)
- The app sends nothing: its only network access is the GitHub release check and the update download (`UpdateService`). Never add analytics, crash reporting or any other phone-home; README's Privacy section promises this.
- Build tools are opted out wherever possible: `Sources/Directory.Build.targets` replaces Avalonia.BuildServices' `AvaloniaStats` target with an empty one (its only documented opt-out is the `AVALONIA_TELEMETRY_OPTOUT` environment variable); CI workflows and `.claude/settings.json` set `DOTNET_CLI_TELEMETRY_OPTOUT`, `TESTINGPLATFORM_TELEMETRY_OPTOUT`, `AVALONIA_TELEMETRY_OPTOUT` and `DOTNET_NOLOGO`; README gives the developer the one line to set them on a PC. Check new tools and packages for telemetry and opt out of it.
- Security reports go through GitHub's private vulnerability reporting (`SECURITY.md`: latest release only, what's in scope, the release key's fingerprint). GitHub security settings (developer's choice): CodeQL default setup, AI Scan for pull requests, Dependabot and malware alerts, secret scanning with push protection, Copilot Autofix suggestions, and agentic autofix (on by the developer's choice). Never Dependabot security/version update PRs, and never assign alerts to Copilot: its PRs would be Copilot-authored on its own branches, against the author and branch rules. A code scanning or Dependabot alert is fixed by Claude on a `fix/…` branch like any other bug.

## Conventions
- Package versions live only in `Sources/Directory.Packages.props`; shared build settings are in `Directory.Build.props`, style in `.editorconfig`.
- XAML uses compiled bindings (`x:DataType`). For a ComboBox, use `DisplayMemberBinding` and `SelectedValueBinding` with `x:DataType`. Selected values must never be `null`: use `""` for "None" or "Default". Setters bound to `SelectedValue` must ignore `null` (a ComboBox pushes it while it builds), or opening a page rewrites settings.
- Theme colors are our own light/dark `ThemeDictionaries` in `Themes/Theme.axaml`, so Windows 10 and 11 look identical. Icons use the `IconFont` resource, the bundled `MicControl.UI/Assets/Fonts/MicControlIcons.ttf` at the Segoe Fluent Icons code points the XAML writes (`&#xE720;` is the microphone), so every OS shows the same icons; to add one, see the `generated-assets` skill.
- Settings: `%APPDATA%\MicControl\settings.json` (camelCase, hotkeys stored as text like `"Ctrl+F1"`, compatible with MicSwitch 1.x); logs in `%APPDATA%\MicControl\logs\MicControl-yyyyMMdd.log` (daily, last 7 kept, shared by every process under a named mutex). A hand-edited or damaged `settings.json` never crashes the app or gets saved over (`AppSettings.Normalize`, `SettingsStore.LoadError`; details in the `product-behavior` skill). The format starts at version 1 (`AppSettings.CurrentVersion`); bump it only with a migration. Keep the MicSwitch 1.x import working (`LegacyConfigMigrator`, `%APPDATA%\MicSwitch\release\config.cfg`).
- Every new platform capability gets an interface in `MicControl.Core/Platform`, a Windows implementation, a fake in the tests, and a flag in `PlatformCapabilities` if some platforms can't support it.
- Add or extend tests for behavior changes; UI behavior can be tested headlessly with `[AvaloniaFact]`.
- Logging: `[LoggerMessage]` source-generated methods only (the analyzers reject `LogInformation(...)` and costly arguments). The file's level is the `logLevel` setting (About → Log detail, default Debug), applied live through `LogLevelSwitch`. Information for user actions and state changes, Debug for decisions and internals, Trace for high-frequency events. Log what the user did and why the app did something (e.g. which monitor the overlay chose), so a test pass can be followed in the log.
