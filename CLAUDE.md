# MicControl

System-wide microphone mute/unmute with hotkeys, an always-on-top overlay, sounds and a tray icon. Its own app, inspired by MicSwitch by Xab3r.
- **Name**: "MicControl" everywhere (UI, tray, notices via `MainViewModel.AppName`; repo `ChaoticHolon/MicControl`, solution, projects, namespaces, exe, settings folder, mutex, autostart entries, installer, packages). No "NG" or "Next Generation": those pre-1.0 names are gone, and nobody runs those builds, so there is no migration from them.
- **Versioning restarts at 1.0.0** (`<Version>` in `Directory.Build.props`). The pre-rename `v2.0.0` tag and release are deleted once, by the developer, when 1.0.0 is released; that is the only exception to "released history is final". The 2.0.0 install on the developer's PC must be uninstalled by hand (the updater never goes down a version).
- Keep "MicSwitch" only for compatibility: importing `%APPDATA%\MicSwitch` (`SettingsStore` legacy folder, `LegacyConfigMigrator` 1.x type names), taking over old autostart entries (only those whose MicSwitch exe is gone; an installed MicSwitch keeps its own), and the credit "Inspired by MicSwitch by Xab3r" (About page, README).
.NET 10, Avalonia 12.1 UI, C# latest. Solution: `Sources/MicControl.slnx`.
- **License: GPL-3.0-or-later** (developer's choice; `LICENSE`, copyright Chaotic Holon). Everything bundled must be GPL-3-compatible (MIT, BSD, Apache-2.0, zlib, public domain…); never MS-PL, CC-BY-NC, proprietary SDKs or "free for non-commercial use" libraries (BASS, CSCore's MS-PL). `THIRD-PARTY-NOTICES.txt` is generated by `tools/GenerateThirdPartyNotices.cs` (`dotnet run tools/GenerateThirdPartyNotices.cs` from the repo root after any package change; it fails on a package it doesn't know, and CI runs it with `--check`). The exe embeds both files (`Legal/…`), the setup installs them next to it, and About → License opens them (GitHub's copies in a build that isn't installed).

## Platform scope
- **Windows 10 (2004+) and Windows 11 are the only supported platforms right now.** Windows 11 has only been tested in a VM.
- **Linux is next: KDE Plasma 6/Wayland** (no X11 support), first target **CachyOS** and the AUR (Arch-based). Plan: GlobalShortcuts portal for hotkeys, PipeWire for audio, layer-shell overlay, XDG autostart. Prototype hotkeys (portal shortcuts need user approval; true hold-to-talk is the open question) and the layer-shell overlay first: they decide what the Linux version can do.
- **Packaging is native per OS, never Flatpak/Snap/AppImage** (developer's design choice):
  - Windows: the app installs itself (see "Installer and updates") plus the in-app updater, which only installs releases signed with the developer's key (see "Signing").
  - Arch/CachyOS: two AUR `PKGBUILD`s. `miccontrol` builds from the source tag with `dotnet publish`; `miccontrol-bin` repackages the release's `miccontrol-<version>-linux-x64.tar.gz`. Framework-dependent on Arch's `dotnet-runtime`, installed system-wide (`/usr/lib/miccontrol`, `/usr/bin/miccontrol` launcher, `/usr/share/applications` desktop file, hicolor icons); settings in `~/.config/MicControl`. Updates come from pacman/shelly/paru/yay. Create and maintain pacman repo later.
  - Debian/Ubuntu: a `.deb` later, built in CI with `nfpm` (one config can also emit an Arch package).
  - Release tag outputs: Windows setup.exe, Linux tarball, signed `SHA512SUMS`; then bump the AUR `pkgver` and checksums.
  - On Linux the `IUpdateService` reports "managed by your package manager" and the About page says so: no in-app updates there.
- Timeline: Linux (CachyOS) release targeted this year, macOS next year.
- macOS plan: Avalonia head project, CoreAudio mute, CGEventTap hotkeys (needs Input Monitoring/Accessibility permission), floating click-through overlay window.
- **Dev's decision: no money to Apple for a developer account, so no notarization. Will likely be distributed as:
  - A Homebrew tap (GitHub repo) whose formula builds from source with `dotnet publish`: locally built apps aren't quarantined, so Gatekeeper doesn't block them, and `brew upgrade` handles updates. Not the official homebrew-cask, which is phasing out casks that fail Gatekeeper.
  - A `.dmg` on GitHub Releases for non-Homebrew users, documenting the one-time System Settings → Privacy & Security → "Open Anyway" step.
  - Sign with a self-made certificate kept in CI secrets (not Apple-issued): a stable identity keeps the Input Monitoring/Accessibility grants across updates. Ad-hoc signing (`codesign -s -`) would satisfy Apple Silicon but loses the grants on every update.
  - In-app updates for the `.dmg` via NetSparkleUpdater behind `IUpdateService` (files the app downloads itself aren't quarantined); Homebrew installs report "managed by Homebrew".
- The developer works with **Visual Studio Enterprise** and **Sublime Text** only; never suggest VS Code or JetBrains tooling.

## Commands (run from `Sources/`)
- Build: `dotnet build MicControl.slnx`. Warnings are errors, and the analyzers are strict (`AnalysisLevel=latest-recommended`).
- Test: `dotnet test --project MicControl.Tests` (Microsoft Testing Platform, opted into by the repo-root `global.json`, so it works from any folder; the old `dotnet test <proj>` form fails).
- Run (Windows): `dotnet run --project MicControl`. The app asks for elevation (`highestAvailable`), so run from an elevated terminal or Visual Studio started as administrator.
- Tests already run on both Windows and Linux. The Windows projects also build on Linux (`EnableWindowsTargeting`).
- Screenshots for the README and releases (the bundled icon font makes Linux renders match Windows, apart from the About page's system details): set `MICCONTROL_SCREENSHOTS=1` and run the tests; `ScreenshotTests` renders the real windows (headless Skia, sample data, light and dark, greyscale text) into `docs/screenshots`. Re-run after visible UI changes and commit the images.
- Setup (from the repo root): `installer\build.ps1 [-Version 1.0.0]` publishes the app as one self-contained file and writes `artifacts\MicControl-Setup-<version>.exe`. CI builds it for every push to `master`/`dev` and every PR; a `vMAJOR.MINOR.PATCH` tag on `master` publishes it as a GitHub release (see "Branches").

## Installer and updates
- **No installer framework** (no Velopack, Inno Setup, WiX, MSIX): the developer requires the installer to look like the app, with its theme, light/dark while using the Windows accent colors, and only Avalonia can do that. Inno Setup was examined and dropped: its styles hard-code their own accent colours.
- **The app installs itself.** The release file `MicControl-Setup-<version>.exe` is MicControl.exe published single-file. `SetupCommand` (Core `Installation/`) decides per launch: a file named `MicControl-Setup*`, or `--install`, shows the installer; `--uninstall` (what Settings → Apps runs) shows the uninstaller; anything else runs the app. Setup mode composes only logging and `IInstaller` (it never loads or imports settings) and shows `Views/InstallerWindow` with `InstallerViewModel`, styled with the app's own theme. `--silent`, `--scope=all|user` and `--relaunch` drive unattended installs and updates.
- Two scopes (`InstallLayout`): all users (the default, developer's choice) → `Program Files\MicControl`, HKLM Apps entry, common Start menu, needs admin (a non-admin setup restarts itself elevated with the choice carried on the command line); just me → `%LOCALAPPDATA%\Programs\MicControl`, HKCU, the user's Start menu, no admin. The Apps entry is `Uninstall\MicControl`, named MicControl; the shortcut is "MicControl".
- Installed layout: `MicControl.exe` (single file; Avalonia's native libraries unpack to `%TEMP%\.net\MicControl` on first start, and the .NET host restores any missing files) plus `Resources\Notifications\*.wav`, `LICENSE.txt` and `THIRD-PARTY-NOTICES.txt`, written from resources embedded in the exe (`Sounds/…`, `Legal/…`, see MicControl.csproj). Each user's settings, logs and added sounds stay in their own `%APPDATA%\MicControl`; uninstall never touches them.
- `WindowsInstaller` (MicControl.Windows): closes running copies (the session exit signal, `WindowsPlatform.ExitSignalName`, asks them to exit cleanly; stragglers such as other users' copies are ended), copies itself via a staging file, writes the sounds, registers the Apps entry and creates the shortcut. Uninstall removes autostart (`StartupService.RemoveAllFor`), the shortcut and the Apps entry, then a hidden PowerShell waits for the process to exit and deletes the folder and this user's unpack cache.
- "Start with Windows" when elevated is a per-user scheduled task `\MicControl\<user> (<domain>)` (`StartupService.TaskName`), so users of an all-users install don't overwrite each other; non-elevated uses the user's own Run key. Uninstall removes every task in `\MicControl\` that starts the uninstalled copy, then the folder if it's empty, plus the current user's Run key value.
- In-app updates (`UpdateService`, logic in Core `Updates/ReleaseFeed`): read the latest GitHub release, and offer it only if its `SHA512SUMS.sig` is a valid signature of its `SHA512SUMS` by a key in `ReleaseKeys.Trusted` and that file lists the setup (checked when looking for updates, so an update that can't be installed is never shown). GitHub's own SHA-256 digest doesn't count: anyone who can edit the release can change it. Verify the download against the signed SHA-512 (a mismatch deletes it and never falls back), run it with `--install --silent --scope=<this install's> --relaunch`, and exit (the new copy starts the app again). Each download goes to a new `%TEMP%\MicControl-update-*` folder (older ones are removed), and the verified file stays open, read-only for others, until the setup has started. A standard user's update of an all-users install runs the elevated copy without `--relaunch` and waits for it; the user's own copy then starts the app, so it never runs as the administrator who approved the prompt. A copy counts as installed when it runs from one of the two install folders (`IInstaller.Current`); dev builds aren't, so they only link to the releases page.

## Product decisions (from the developer)
- Default mode is Push-to-talk; Toggle and Push-to-mute are alternatives. State at startup (Toggle only) defaults to Muted. "Exclusive hotkey" (suppress) is off by default.
- A MicSwitch 1.x import brings hotkeys, microphone, sounds, overlay and window settings, but never MicSwitch's mode or startup state (new users always get Push-to-talk and Muted), and setup still runs so the imported values can be reviewed. Imported custom hotkeys and non-default sounds stay switched off; setup's last step asks whether to use them (`OffersImportedCustomHotkeys`/`OffersImportedSounds`).
- Close to the tray (`window.appMode` in settings, kept for compatibility; `IsTrayMode`): one on/off switch on Home, in setup's last step and in the tray menu, described by `CloseToTrayDescription`. Users never see "App mode", "Tray mode" or "Window mode"; keep it that way. On (default) starts hidden, including at sign-in; Close and Minimize hide to the tray, with a once-per-session notice that has "Don't show again". Off is a normal app: Close exits, Minimize goes to the taskbar. First run always shows the window, for setup.
- Shutdown and resilience (`App.axaml.cs`, `AppShutdown`):
  - A session end (shutdown, restart, sign-out, Restart Manager) always exits cleanly, in both modes, once Windows confirms it (WM_ENDSESSION): `WindowGuard` answers the WM_QUERYENDSESSION for Avalonia's message window, so the app keeps running if another app vetoes the shutdown. The log is flushed (`FileLoggerProvider.Flush`) before WM_ENDSESSION returns and keeps logging. It never hides to the tray, which would veto the restart. Avalonia's `ShutdownRequested` still exits on platforms without the guard.
  - Otherwise the overlay and hidden main window refuse every close (an external close of the hidden main window shows no tray notice). `WindowGuard` makes the hidden helper windows refuse closes too, on every thread of the process: Avalonia's `AvaloniaMessageWindow` (dispatcher posts, timers, tray icon), its `AvaloniaSimpleWindow`s (on the UI thread one owns the overlay, and Windows destroys owned windows with it; another lives on a background thread), and the IME windows. It rescans whenever one of our windows opens, and logs each helper it protects (name, handle, thread) or fails to watch. UI-thread windows are subclassed with comctl32; other threads' windows get their window procedure replaced, so their messages are handled (and logged) on their own thread, and only the UI thread's windows start the exit. External closes (e.g. `taskkill` without `/F`) are refused and logged as Warnings. Destroying the message window was the "zombie" bug (tray icon gone, hotkeys dead, process alive); destroying the hidden window that owns the overlay crashed the next mute change. If the overlay is destroyed anyway, `App` replaces it with a new one.
  - `IWindowInterop.WatchLifecycle` (`WindowLifecycleWatcher`, a Win32 subclass) logs WM_CLOSE, SC_CLOSE, WM_QUERYENDSESSION, WM_ENDSESSION and WM_DESTROY at Information, with flags, sent or posted, and the foreground process.
  - A `UiWatchdog` pings the UI thread every 20 s. After 3 misses it releases the hook, flushes the log, starts a fresh copy (`--relaunched-from=<pid>`, which waits for the old copy to exit) and ends with exit code 3.
  - When the main loop returns, `Program` calls `App.OnMainLoopEnded`, which cleans up if our exit didn't run, then `Environment.Exit`.
- Start with Windows is on by default: a new user's first run of an *installed* copy enables it (`ApplyFirstRunDefaults`; per user, so each user of an all-users install gets it on their own first run). Dev/portable builds never register themselves, and existing or imported users keep their choice. Setup shows the toggle, so it's easy to turn off.
- The tray icon is always shown. Left-click (or double-click) never changes state; it opens the full window. There is no quick popup (the developer dropped it: the right-click menu already has those controls). Right-click: Open · Mute/Unmute · Mode · Microphone · Overlay · Play sounds · Close to the tray · Start with Windows · Exit.
- About → Advanced (always shown, between Updates and System: settings first, then the read-only details) holds the optional features, both off by default: **Custom hotkeys** (`customHotkeysEnabled`) adds the **Hotkeys** page and **Custom sounds** (`notifications.customSoundsEnabled`) adds the **Sounds** page. A switch is named "Custom X" and its page plainly "X"; keep that pattern. Their tabs come after About, in the order of the switches (Home · Overlay · About · Hotkeys · Sounds), and only show while the switch is on (`NavItems` is filtered from `AllNavItems`; a hidden page navigates Home). Off pauses custom hotkeys and plays the built-in cues at full volume on the default device (`NotificationSettings.Played*`); the user's rows and choices are kept for when it's turned back on. Basic settings (Play sounds, overlay, etc.) stay on Home.
- Custom hotkeys are a dynamic list of key → action rows; the action list hides whatever the main key already does in the current mode.
- A held hotkey whose key-up never arrives (Win+L or a UAC prompt while holding push-to-talk) is released after two 250 ms checks find the key up (`GlobalHotkeyService.ReleaseMissedKeyUps`), so push-to-talk never stays live. Exclusive hotkeys are skipped: a key the hook swallows never shows as down.
- A microphone that is plugged back in (or newly bound) gets the app's last mute state and kept volume (`AudioEndpointGroup.Rebind`), in every mode, not just "All microphones".
- Overlay is a translucent Discord inspired badge, positioned by corner presets or "Edit position" (drag); click-through otherwise. "Show overlay" is a four-stop slider, Never → When muted → When live → Always (`OverlayVisibilityStep`), not a dropdown.
- Home's sections: Microphone (device, Mode, key, Input volume, whose slider only shows while it's kept), Overlay and sounds, App (Start with Windows, Close to the tray, Theme). Every row has a description except where the header says it all.
- Sliders in rows use `Slider.row` + a `TextBlock.sliderValue` column (same width and position on every page, and no taller than a switch row). Custom hotkey rows put the action on the left and the on/off switch and delete on the right, like every other row. Setup's rows are plain (`Border.setupCard`), not cards in a card, and reuse the Overlay page's four corner buttons.
- Pages share one top: title, a one-line subtitle (`pageSubtitle`, on every page), then on Home and About the same card (`Border.hero`: 56 px icon, `heroTitle`, `heroDetail`, `heroAction` button). About's icon follows the live/muted state like the rest of the app.
- Home's Mode (Push-to-talk | Toggle | Push-to-mute, `IsPushToTalkMode`/`IsToggleMode`/`IsPushToMuteMode`) and Theme (System | Light | Dark, `IsSystemTheme`/`IsLightTheme`/`IsDarkTheme`) are segmented controls (`Border.segmented` + `RadioButton.segment`), not dropdowns or sliders: a few peers with no order use the pill; an ordered scale (Show overlay) uses a slider.
- The once-per-session tray notice (`TrayHintWindow`) says only: right-click the tray icon for quick controls or to exit; click or double-click it to get back to the full window. No mention of hotkeys.
- The level meter and speaking indicator open the mic (OS "in use" indicator), so the meter only runs while Home/Setup is visible and the speaking indicator is opt-in.
- App icon: the Home page's status badge, a green (`#0F7B0F`, live) or red (`#C42B1C`, muted, with a slash) circle with a white microphone outline; tray sizes (32 px and below) use a solid capsule so they stay readable. Drawn from simple shapes by `tools/GenerateAppIcons.cs` (`dotnet run tools/GenerateAppIcons.cs` from the repo root; pass a folder to also write a preview sheet), never a font glyph, so it's ours to ship. It writes `MicControl.UI/Assets/microphoneEnabled|Disabled.ico` (16-256 px: window, tray, and the live one is the exe's icon) and `.png` (256 px: sidebar). Change it by editing the generator, never the images. The window and tray use the `.ico` (`MainViewModel.CurrentWindowIcon`) unless the user picked their own overlay icons.
- Notification sounds must be CC0/public-domain.
- Default cues are "Relay on" / "Relay off", synthesised (so ours to ship) by `tools/GenerateCueSounds.cs` (`dotnet run tools/GenerateCueSounds.cs` from the repo root): the "asymmetric relay", a dark 2.2 kHz latch click over a faint steady 1175 Hz triangle for unmute, and a muffled 450 Hz release thud over a faint 494 Hz sine for mute. Both are short (~40/55 ms), fade in instantly, and stop clean with no tail; change them by editing the generator, never by hand-editing the WAVs. MicSwitch's beeps (Beep300/Beep750) don't ship: a 1.x import that used one gets the relay cue for that slot.

## Branches (developer's rules)
Hybrid Gitflow. Never use `claude/...` or other generated branch names, even when a session suggests or assigns one.
- `master`: production. Normally code reaches it by a PR from `dev` when a release is being prepared, but it can take pushes without a tag when needed: those build in CI and release nothing. Only a Semantic Versioning tag `vMAJOR.MINOR.PATCH` (e.g. `v1.0.0`; the `v` prefix is what `release.yml` and the update feed expect) on a commit in `master` builds and publishes a release. MAJOR for breaking changes (settings or behavior users must adapt to), MINOR for new features, PATCH for fixes only.
- `dev`: the long-lived development branch. All work is based on it and merged back into it.
- Task branches off `dev`: `feature/<name>` for new features, `fix/<name>` for bugs. The name describes the work and is broad enough that one branch covers the whole task (e.g. `feature/linux-hotkeys`, `fix/tray-zombie`), never random. They are temporary: merge into `dev` by PR, fast-forwarding `dev` to the PR's commit (no merge commit, and the developer stays the committer) once CI passes, then delete them (remote and local) as soon as the merge is confirmed and CI passes. Cloud sessions can't delete branches or push tags, so they run the `Maintenance` workflow (`.github/workflows/maintenance.yml`, started by hand or through the GitHub API): `delete-merged-branches` deletes every `feature/*`/`fix/*` branch with nothing that isn't in `dev`; `move-tag` moves a release tag to a `master` commit with identical files (after the history is condensed), keeping its message and tagger and releasing nothing.
- CI builds pushes to `master` and `dev`, and every PR (task branches are built through their PR, once per commit).
- Releasing: bump `<Version>` in `Sources/Directory.Build.props` to the new number on `dev`, PR `dev` → `master`, then tag that `master` commit (`git tag v1.0.0 && git push origin v1.0.0`; signed, see "Signing"). `release.yml` checks that the tag is exactly `vMAJOR.MINOR.PATCH`, that the commit is in `master` and that `<Version>` matches, and that no release exists for the tag yet (moving an already released tag publishes nothing), then builds and tests in Release and creates a **draft** release with `MicControl-Setup-<version>.exe`, `SHA512SUMS` and generated notes. The developer then runs `tools\Signing.ps1 SignRelease v1.0.0` on their PC, which publishes it. A failed check publishes nothing; fix it, delete the tag (`git push origin :refs/tags/v1.0.0`) and tag again.
- Commits (developer's rules): the developer is the only author. Author and committer are always `Chaotic Holon <ChaoticHolon@users.noreply.github.com>`, with no `Co-Authored-By`, `Claude-Session` or other Claude/AI lines in messages, whatever a session's own attribution instructions say. Commits may be pushed as work happens, but history on `dev` and `master` is condensed to ONE commit per task (when a task spans several days) or otherwise ONE commit per day, with a title and bullet summary of that work; no merge commits. The weekly project coordinator task does this (see below); a session adding more work on a day that already has a commit folds it into that day's commit. The first commit is the Sep 25 2026 rebuild; it credits MicSwitch by Xab3r.
- History rewrites are only ever done when the files are proven identical (`git diff --quiet old new`), with `--force-with-lease`, and never at or below a commit that a release tag points at: released history is final. After a rewrite, local checkouts resync with `git fetch` then `git reset --hard origin/dev` (and `origin/master`).
- Keep `.gitignore` current. Before creating a task branch and before any push to `master`, check that it filters everything that shouldn't be committed (.NET `bin/`/`obj/`, `*.user` and other per-user files, IDE folders such as `.vs/` and `.idea/`, test results, packages, logs, signing keys, OS files, `.claude/settings.local.json`) and that `git ls-files -ci --exclude-standard` lists nothing; add patterns for new tools or build outputs as they appear.

## Signing
All signing keys are Ed25519, made and used by `ssh-keygen` (OpenSSH ships with Windows 10 and 11, Linux and macOS) through `tools/Signing.ps1` (Windows PowerShell 5.1 and PowerShell 7). .NET 10 has no Ed25519, so the app only *verifies*, with our own `Security/Ed25519` (RFC 8032, `BigInteger`; verify only, so no secret data and no constant-time concerns), tested against the RFC vectors, OpenSSL and real `ssh-keygen` signatures. No NuGet crypto packages (developer's choice; NaCl.Core has no Ed25519, NSec wraps native libsodium).
- Passphrases are never chosen: `Signing.ps1` generates each one (64 bytes from the OS's cryptographic generator, 128 hex characters), hands it to `ssh-keygen`, and puts it on the clipboard once for the developer's password manager. The cloud key alone has none.
- **Release key** (`~/.miccontrol/release_signing_ed25519`, generated passphrase pasted at every `SignRelease`, on the developer's PC only, never in CI): `SignRelease` downloads the draft, checks every file against `SHA512SUMS`, checks that the tag's `docs/release_signers` trusts the key, signs (`ssh-keygen -Y sign -n miccontrol-release`), verifies with OpenSSH, uploads `SHA512SUMS.sig` and publishes. The public keys live twice, kept equal by a test: `ReleaseKeys.Trusted` (built into the app) and `docs/release_signers` (allowed-signers format, for `ssh-keygen -Y verify` by users, the script and future AUR packages). Rotation: ship a version trusting old and new key, sign later releases with the new one, drop the old a release later. Losing the key means installed copies can't update in-app until a new version is installed by hand, so the developer keeps an offline backup.
- **Commit signing** (GitHub "Verified"): `GitSigning` sets up the developer's PC (`~/.ssh/github_signing_ed25519`, its generated passphrase pasted once into `ssh-add`, then kept by the Windows SSH agent, `gpg.format ssh`, `commit.gpgsign`/`tag.gpgsign`, Windows' own `ssh-keygen` as `gpg.ssh.program` so Visual Studio and Git for Windows use the agent). Cloud sessions sign with a separate, revocable key (`CloudKey`): the environment variable `MICCONTROL_GIT_SIGNING_KEY` (base64 private key) is turned into git config by the SessionStart hook `.claude/hooks/git-signing.sh`, which does nothing without the variable or `ssh-keygen`. Both public keys are registered on GitHub as Signing Keys. The cloud environment also signs commits by itself (`gpg.ssh.program` is the platform's `/tmp/code-sign`, with a key that isn't on the developer's account); with the variable set, the hook points `gpg.ssh.program` back at `ssh-keygen` so the cloud key signs instead.
- `Security/SecretBox` (not used yet): authenticated encryption for local data, ChaCha20-Poly1305 where .NET has it (Windows 11, Linux, and macOS through CryptoKit, still to be confirmed on a Mac; not Windows 10, which needs build 20142), otherwise AES-256-GCM; layout algorithm byte · 12-byte nonce · ciphertext · 16-byte tag. It needs a key from somewhere safe (e.g. DPAPI on Windows, the keychain on macOS) before anything uses it; settings stay plain, hand-editable JSON.

## Roadmap (developer's plans; nothing built yet)
MicControl grows from mic muting into voice processing and mixing. None of it is in 1.0; keep the current design open to it.
- **Audio engine**: a separate `MicControl.Audio` project behind `MicControl.Platform` interfaces. 10 ms blocks (480 samples at 48 kHz) through preallocated ring buffers; the audio thread never allocates and runs at MMCSS "Pro Audio" priority. Keep NAudio (MIT) for devices; for a cross-platform engine consider miniaudio (public domain/MIT-0, P/Invoke). Not CSCore (abandoned, MS-PL) or BASS (proprietary).
- **Speech enhancement**: GPU-first via ONNX Runtime (DirectML on Windows, CUDA/TensorRT, Core ML on macOS), with posted system requirements and a benchmark on the user's own machine before it can be turned on (it stays off, with the reason, if it can't keep up). The developer rejects DeepFilterNet (unmaintained) and RNNoise (robotic). First prototype ClearerVoice-Studio's models (MossFormer2) streaming in a sliding window, measuring latency (target 20-40 ms look-ahead) and quality; ClearerVoice also suits cleaning saved clips. Echo cancellation: WebRTC AEC3. Windows 11's Voice Clarity is a possible light fallback. Check every model's licence (e.g. Meta's denoiser weights are CC-BY-NC: not shippable).
- **Per-app capture** (Discord, Spotify… by PID): WASAPI process loopback (`ActivateAudioInterfaceAsync` with `AUDIOCLIENT_ACTIVATION_TYPE_PROCESS_LOOPBACK`, Windows 10 2004+, our minimum), likely our own interop feeding NAudio; macOS ScreenCaptureKit (13+) or Core Audio process taps (14.4+); PipeWire natively.
- **Three output buses** (headphones, OBS, recording) with sub-mixes. Open question before building it: getting a bus to OBS/Discord on Windows normally needs a virtual audio device (a kernel driver, which needs an EV certificate and Microsoft attestation signing, a yearly cost); alternatives are an OBS plugin, OBS's application capture, or VB-Cable if installed.
- **Device aliases**: custom names for devices, keyed by device id in settings (small; could ship in a 1.x).
- Later: a clip recorder writing the recording bus to disk; macOS audio core (Core Audio HAL, ScreenCaptureKit); network control and streaming (OSC, a VBAN-compatible protocol).

## Privacy and telemetry (developer's rule)
- The app sends nothing: its only network access is the GitHub release check and the update download (`UpdateService`). Never add analytics, crash reporting or any other phone-home; README's Privacy section promises this.
- Build tools are opted out wherever possible: `Sources/Directory.Build.targets` replaces Avalonia.BuildServices' `AvaloniaStats` target with an empty one (its only documented opt-out is the `AVALONIA_TELEMETRY_OPTOUT` environment variable); CI workflows and `.claude/settings.json` set `DOTNET_CLI_TELEMETRY_OPTOUT`, `TESTINGPLATFORM_TELEMETRY_OPTOUT`, `AVALONIA_TELEMETRY_OPTOUT` and `DOTNET_NOLOGO`; README gives the developer the one line to set them on a PC. Check new tools and packages for telemetry and opt out of it.

## Conventions
- Package versions live only in `Sources/Directory.Packages.props`; shared build settings are in `Directory.Build.props`, style in `.editorconfig`.
- XAML uses compiled bindings (`x:DataType`). For a ComboBox, use `DisplayMemberBinding` and `SelectedValueBinding` with `x:DataType`. Selected values must never be `null`: use `""` for "None" or "Default". Setters bound to `SelectedValue` must ignore `null` (a ComboBox pushes it while it builds), or opening a page rewrites settings.
- Theme colors are our own light/dark `ThemeDictionaries` in `Themes/Theme.axaml`, so Windows 10 and 11 look identical. Icons use the `IconFont` resource: the bundled `MicControl.UI/Assets/Fonts/MicControlIcons.ttf` ("MicControl Icons"), Microsoft's Fluent UI System Icons (MIT, licence beside the font) subset to the icons we use and placed at the Segoe Fluent Icons code points the XAML writes (`&#xE720;` is the microphone), so every OS shows the same icons. `tools/GenerateIconFont.py` builds it (`pip install fonttools`, then `python tools/GenerateIconFont.py` from the repo root): to add an icon, add its Segoe code point and Fluent name to `ICONS` and run it again; never edit the font by hand.
- Settings: `%APPDATA%\MicControl\settings.json` (camelCase, hotkeys stored as text like `"Ctrl+F1"`); logs in `%APPDATA%\MicControl\logs\MicControl-yyyyMMdd.log` (a new file each day, also while running; last 7 kept; every process logging to the folder, such as the app and its setup, shares the file and appends under a named mutex). A hand-edited `settings.json` with `null` sections, rows or hotkeys loads with defaults in their place (`AppSettings.Normalize`); a failed save is retried and never crashes. The settings format starts at version 1 (`AppSettings.CurrentVersion`); bump it only with a migration. Keep the MicSwitch 1.x import working (`LegacyConfigMigrator`, `%APPDATA%\MicSwitch\release\config.cfg`), and keep hotkey strings compatible with MicSwitch 1.x.
- Every new platform capability gets an interface in `MicControl.Core/Platform`, a Windows implementation, a fake in the tests, and a flag in `PlatformCapabilities` if some platforms can't support it.
- Add or extend tests for behavior changes; UI behavior can be tested headlessly with `[AvaloniaFact]`.
- Logging: `[LoggerMessage]` source-generated methods only (the analyzers reject `LogInformation(...)` and costly arguments). The file's level is the `logLevel` setting (About → Log detail, default Debug), applied live through `LogLevelSwitch`. Information for user actions and state changes, Debug for decisions and internals, Trace for high-frequency events. Log what the user did and why the app did something (e.g. which monitor the overlay chose), so a test pass can be followed in the log.
